**三条硬性架构约束**：

1. **算法与框架解耦**：全部分解算法、守恒断言、弹性估计放在 `packages/attribution`，**禁止 import** FastAPI / SQLAlchemy / 任何网络或数据库客户端，保证可用纯函数单测、可被脚本直接复用。
2. **数值不经过大模型**：LLM 只产出假设文本、SQL 草案与报告文字；所有数值由 `packages/attribution` 与数据库计算。
3. **沙箱是唯一执行外部代码的出口**：任何由模型生成的 SQL / Python 都必须经沙箱执行器，服务进程内不直接执行。

**为什么不是 PostgreSQL（v1.1 变更）**：本机无 PostgreSQL 实例、Docker 守护进程常不启动（均实测），而 SQLite 零安装，
且只读性可以用 `file:...?mode=ro&immutable=1` 当场验证。取舍与代价见 [`04-决策记录.md`](04-决策记录.md) D-22；
本文件 §3、§6、§7 已按 SQLite 口径改写，与需求侧规格不冲突。

## 3. 数据模型

### 3.1 `dw` schema：合成星型数仓

| 表 | 粒度 | 规模 | 说明 |
| --- | --- | --- | --- |
| `dw.dim_date` | 天 | 546 | 日期、月、季、是否大促、大促名称、季节性因子、大促倍率 |
| `dw.dim_channel` | 渠道 | 8 | 自然搜索 / 付费投放 / 私域 / 直播 / 短视频 / 商超 / 经销商 / 餐饮，含是否付费标记 |
| `dw.dim_category` | 品类 | 12 | 支持两级（父类 / 子类） |
| `dw.dim_region` | 区域 | 7 | 华东 / 华南 / 华北 / 华中 / 西南 / 西北 / 东北 |
| `dw.dim_segment` | 客群 | 5 | 新客 / 高价值老客 / 价格敏感 / 沉默召回 / 企业客户 |
| `dw.dim_sku` | 物料 | 40 | 快消品 SKU，含标准单位成本 |
| `dw.fact_ecom_daily` | 天 × 渠道 × 品类 × 区域 × 客群 | 实测 1,009,706 | 电商漏斗与成交：impressions / clicks / visitors / add_to_cart / orders_created / orders_paid / units / gmv_cents / refund_cents |
| `dw.fact_order` | 订单 | 实测 1,920,179 | 订单明细（支撑"下钻到底层行为事实"）：订单号、时间、渠道、品类、区域、客群、件数、金额（分）、状态（paid / refunded / cancelled） |
| `dw.fact_fmcg_daily` | 天 × 渠道 × SKU × 区域 | 实测 1,223,040 | 快消经营：revenue_cents、raw_material_cents、logistics_cents、channel_commission_cents、other_cost_cents、units |

**设计要点**

* 金额一律以**整数分**存储，聚合不产生浮点误差。
* `fact_order` 与 `fact_ecom_daily` 存在冗余（后者是前者的日聚合），**这是有意的**：聚合表用于大盘与一级拆解的性能，明细表用于下钻验证；两者的一致性用"日粒度对账断言"保证（聚合表 == 明细表按同维度汇总）。
* 规模实测：三张事实表 **4,152,997 行**（P2 完整档，2026-09-15），加 13,468,481 条索引条目后 `dw.db` 为 628.6 MB；
  生成 38.2 s、重置 0.08 s ⇒ **O-01 不触发**（保持 546 天，不下调到 200 万行）。命令与解释见 `03-进度与质量` §6。
* 订单明细比原估的 160 万高约 20%：大促倍率（1.4~3.2 倍）与周末效应计入后支付单总量上浮——这是实测结果，不为凑数字改口径。
* `visitors ≡ clicks`：指标树把 `CTR` 定义为 `clicks / impressions`、`UV` 定义为 `visitors`，要严格满足 `UV = 曝光 × CTR`，
  生成器就必须令访客数等于点击数。这是**有意为之的定义式**，不是数据错误。

## 5. 算法规格

### 5.1 差额分析（加法结构）

对 `Y = Σ xᵢ`：`ΔY = Σ Δxᵢ`；因子贡献 `cᵢ = Δxᵢ`；贡献率 `rᵢ = Δxᵢ / ΔY`（**仅当 ΔY ≠ 0**，否则只输出 `cᵢ` 并标记 `rate_undefined = true`）。

### 5.2 LMDI（乘法结构）

对 `Y = Π xᵢ`：

```
ΔY = Σ L(Y₁, Y₀) · ln(xᵢ₁ / xᵢ₀)
L(a, b) = (a − b) / (ln a − ln b)      # a ≠ b
L(a, a) = a                            # 极限情形，避免除零
```

**约束与预案**：

* 要求所有因子严格大于 0。
* **零值预案 A（替换）**：把 0 替换为 `ε = max(1e-9, 该因子历史最小值 × 0.01)`，结果标记 `zero_substituted = true`，报告需展示该标记。
* **零值预案 B（降级）**：若替换会显著扭曲结果（替换后因子排序改变），降级为**分步差分**（先变因子甲、再变因子乙），标记 `method = staged_diff`。
* 无论走哪条路径，**必须通过守恒断言**，否则抛错而不是静默返回。

### 5.3 混合树分解

按指标树节点递归：每个节点声明 `method = diff | lmdi`，逐层分解并**逐层独立守恒**；层与层之间不得互相抵消。任一节点断言失败即整次分解失败（不允许局部通过）。

### 5.4 守恒断言（全项目统一实现）

```python
def assert_conservation(contributions, delta, tol=1e-9) -> float:
    residual = abs(sum(contributions) - delta)
    relative = residual / max(abs(delta), 1.0)
    if relative >= tol:
        raise ConservationError(residual=residual, relative=relative)
    return residual      # 返回实际残差，写入接口响应与报告
```

**只允许存在这一个实现**，任何模块不得自行比较浮点数。

### 5.5 维度贡献：优先精确，其次分摊

* **优先**：按维度组合直接计算该组合的贡献（加法用该组合的差值；乘法按 5.2 在该组合内计算）。数学上 `Σ_组合 贡献 = 总贡献`，因此**精确且守恒**。
* **降级**：仅当某切片缺数据或因子在该切片内无法定义时，退化为**按占比分摊**（`c(d) = ΔY × 该切片占比变化 / Σ|占比变化|`），并标记 `heuristic = true`——报告中必须说明这是启发式结果、非唯一解。

> 这一条的排序很重要：**能精确计算却去用分摊，是偷懒；用分摊而不标注，是误导。**

### 5.6 弹性估计（What-If 基础）

* **主路径**：对数-对数回归 `ln(Y) ~ ln(x)`，斜率即弹性；至少 60 个观测点。
* **降级**：样本不足时用有限差分（`ΔY/Y ÷ Δx/x`），并放宽输出区间。
* **区间**：用 bootstrap（固定种子，默认 1000 次）给出 90% 区间。
* **可干预性**：只有标记为 `intervenable = true` 的因子允许进入 What-If。

### 5.7 统计检验

* **显著性**：置换检验（默认 10000 次，固定种子）——`p = (1 + #{|统计量置换| ≥ |统计量观测|}) / (1 + B)`。
* **相关性**：Spearman 秩相关 + 置换显著性（不假设正态分布）。
* **效应量**：连续量用标准化差异，比率量用绝对风险差，二者都落库并与 p 值一同展示。

### 5.8 置信度合成

```
confidence = 0.40 × 显著性得分 + 0.35 × 效应量得分 + 0.25 × 数据覆盖度得分
显著性得分：p < 0.01 → 1.0；p < 0.05 → 0.7；p < 0.10 → 0.4；否则 0
效应量得分：按效应量的分档阈值线性映射（阈值写入配置）
数据覆盖度：实际覆盖天数 ÷ 要求覆盖天数，上限 1.0
```

低于阈值（默认 0.6）→ 状态置为 `excluded`，**并把 reason 与证据一起展示**，不得静默丢弃。

### 5.9 伪相关四步（实现对应）

| 步骤 | 实现 |
| --- | --- |
| 1 控制变量 | 在关键维度切片内部重跑同一检验；切片内不显著 → 判为共同驱动 |
| 2 时间先行性 | 比较原因与结果的首次显著变动时点；原因晚于结果 → 下调置信度 0.3 |
| 3 安慰剂维度 | 在"理论上不应成立"的维度上做同样检验；同样显著 → 判为趋势性共同驱动 |
| 4 样本充分性 | 样本量 < 60 或覆盖 < 21 天 → 结论降级为"证据不足"，不计入主结论 |

### 5.10 事件匹配

`相关度 = 0.6 × 维度重合度 + 0.4 × 时间接近度`；窗口默认前后 3 天。
`相关度 ≥ 0.5` → 入因果链并标记为**外生变量**；`0.3 ~ 0.5` → 只列"待观察"；`< 0.3` → 不展示。

## 6. 数据沙箱：实现与隔离等级

### 6.1 进程模型

* 主服务与沙箱**不在同一进程**：由 `services/attr-api/app/sandbox/runner.py` 以 `subprocess` 启动独立 Python 解释器，通过 stdin/stdout 的 JSON 协议通信（请求：`{kind: sql|python, code, session_id}`；响应：`{ok, rows|result, error, metrics}`）。
* 沙箱进程**不继承**服务进程的环境变量，只注入白名单（`SANDBOX_*` 与数据库只读 DSN）。
* 每次执行写一条 `app.sandbox_runs`（**被拦截的执行也要写**，这是审计与对抗测试的证据来源）。

**落地实现（P3 交付）**：准入规则在 `app/sandbox/policy.py`（sqlglot AST 判定），执行体在 `app/sandbox/child.py`
（只读 DSN 由父进程按 `app/db.open_readonly_connection` 生成后注入），配额与审计在 `app/sandbox/runner.py`。
对抗集在 `corpus/eval/sandbox_adversarial.yaml`，一条命令复现：`python services\attr-api\scripts\run_adversarial.py`。

### 6.2 四道约束

| 约束 | 实现 | 失败时的行为 |
| --- | --- | --- |
| **数据只读** | SQLite 只读打开：`file:dw.db?mode=ro&immutable=1` + `PRAGMA query_only=ON`；业务表根本不在这个文件里，连接里看不见 `app.db` | SQLite 直接拒绝写（`SQLITE_READONLY`），拒绝记录进 `sandbox_runs.blocked_reason` |
| **语句白名单** | P3 起用 `sqlglot` 做 **AST 级**校验：只允许单条 `SELECT`；禁止 DDL/DML/多语句；表名必须命中白名单（`dw.*` 视图） | 拦截并记录 `blocked_reason` |
| **资源配额** | 执行时限（`SANDBOX_TIMEOUT_SECONDS`，硬超时 terminate→kill）；返回行数上限（`SANDBOX_MAX_ROWS`）；内存轮询监控（`psutil`，超 `SANDBOX_MEMORY_MB` 杀进程）；CPU 时间上限 | 杀进程 + 记录超限原因 |
| **无网络** | 子进程内屏蔽 `socket`/`urllib`/`http` 类模块；Python 导入白名单（`numpy`/`pandas`/`math`/`statistics`/`decimal`/`datetime`/`json`）；黑名单（`os`/`sys`/`subprocess`/`socket`/`shutil`/`pathlib`/`importlib`/`ctypes`/`multiprocessing`） | 拦截并记录 |

### 6.3 隔离等级与残余风险（如实声明，不夸大）

**这是进程级隔离，不是容器或虚拟机级隔离。** 能防住的：写入业务库、越权读表、外网访问、无限资源占用、危险模块导入。防不住的：

1. 同机同用户身份下对文件系统的读取（Windows 上无 `rlimit`，我们靠轮询与硬超时兜底，无法做到精确 CPU 计量）；
2. 内核/解释器级漏洞导致的逃逸；
3. 通过间接信道（如极慢查询做侧信道）推断未授权数据的**存在性**——本项目数据为合成数据，该风险可接受。
4. **SQLite 没有数据库角色层**（这是改用 SQLite 最实在的代价）：沙箱读不到业务表，是因为业务表压根不在 `dw.db` 这个文件里、
   且连接以只读方式打开；但如果攻击者已经拿到服务进程的同用户身份，他可以直接读 `app.db` 文件。PostgreSQL 方案下这一层由角色权限挡住，
   现在只能靠 OS 级 ACL 兜底——部署到服务器时必须启用（见下方"加固路线"），本机开发阶段如实声明这一点，不假装它不存在。

**加固路线（部署到服务器时启用）**：独立系统用户运行沙箱进程 + 文件系统 ACL + Windows Job Object / Linux cgroup 限制。以上均记录在案，不伪装成容器级隔离。

### 6.4 对抗测试集（≥10 个用例，拦截率必须 100%）

越权读业务表（`app.db` 里的 `users` / `audit_logs`）、`ATTACH DATABASE` 外挂新文件、多语句拼接、注释绕过、
`readfile()` / `writefile()`、Python `import os`、Python 开 socket、死循环、超大结果集、内存炸弹、写数仓表——每个用例都断言"被拦截 + 有审计记录"。

## 7. 部署与运维

### 7.1 本机开发（不依赖 Docker）

```powershell
# 1) 数仓：SQLite 零安装，建表 + 建索引 + 生成数据一步完成（实测 38.2 s，415 万事实行）
python services\attr-api\scripts\generate_warehouse.py --profile full --reset

# 2) 校验：对账断言 / 指标 SQL / 指标树恒等式 / 真值复核（任一失败即非 0 退出）
python services\attr-api\scripts\verify_warehouse.py

# 3) 只读约束当场验证（沙箱"数据只读"的替代证据）
python infra\sqlite\verify_readonly.py

# 4) 迁移 + 种子（用户、指标字典、事件日历）——P3 出现需演进的业务表时启用
# alembic upgrade head
# python services\attr-api\scripts\seed_app.py

# 5) 起服务与前端
powershell -ExecutionPolicy Bypass -File scripts\dev.ps1
```

### 7.2 上线形态

* 后端：`uvicorn`（`--workers` 注意：SSE 与沙箱状态在单进程内更简单，建议先单进程 + 队列，再谈横向扩展）；宿主 `Nginx` 反代，容器端口不暴露公网。
* 数据库：SQLite 两文件（`dw.db` 可随时由固定种子重建，属于可再生数据；`app.db` 是真实业务数据，需定时备份）。
  备份方式：`app.db` 用 `VACUUM INTO` 做一致性快照（脚本 `scripts/backup_server.ps1`，P7 落）。**不备份 `dw.db`**——
  它是合成数据，重建比备份更快也更可靠（重建 38.2 s vs 复制 628 MB）。
* 冒烟验收：`python scripts\smoke_test.py --base-url http://127.0.0.1:8001` 覆盖 7 项（登录、指标树、异动大盘、发起会话、沙箱拦截记录、报告导出、审计只读）。

## 9. 配置与密钥

* 全部配置走 `.env` + `pydantic-settings`，缺关键项时**启动即失败**（不允许运行时才发现）。
* 密钥（`SECRET_KEY`、`LLM_API_KEY`、数据库口令）只从环境变量读，**禁止写进仓库**；日志中对密钥与长 SQL 一律做摘要化处理（记 `statement_digest` 而非原文）。
* 沙箱相关配置集中在 `SANDBOX_*` 前缀下，便于审计与调参。

## 10. 性能测量方法（数字必须可复现）

* 脚本 `scripts/bench.py`：固定数据集 + 固定查询集合，每项跑 50 次，输出 P50 / P95 / 最大值与错误率。
* 每次测量必须记录：**命令、日期、机器规格、数据行数、并发数**，写入 `services/attr-api/eval/bench_<label>.json` 与 `03-进度与质量.md`。
* 对外数字只允许来自**完整档**（见 `02-流程与规范` 第 3 节）的实测结果；跑不出同量级数字时，从 README 与材料中撤下。
