# 底座怎么读：数仓、指标树与分解引擎的边界

> 版本：v1.1（P2 数据底座 + P3 分解与沙箱）　｜　日期：2026-09-15
> **用途**：第一次打开这个仓库的人，用 15 分钟建立"哪段代码在哪、为什么这么分"的心智模型。
> 只讲"为什么这么写"，不复述代码；具体实现细节看文件顶部的 docstring。

## 1. 依赖方向只有一个方向

```
apps/attr-web  ──►  services/attr-api  ──►  packages/attribution
（P5 起）            （路由 / 用例 / 数仓层）    （纯算法，无 IO、无框架）
                     └── app/warehouse/ 直接读 SQLite（dw.db）
```

**`packages/attribution` 里不允许出现 FastAPI / SQLAlchemy / 任何数据库或网络客户端**（`01-技术规格` §1 第一条硬约束）。
理由很实际：分解公式的正确性必须能用纯函数单测验证，也因为"算法要能脱离 Web 服务被脚本直接复用"。

## 2. 数据底座这条线，按这个顺序读

| 步 | 文件 | 你会知道什么 |
| --- | --- | --- |
| 1 | `app/warehouse/dw_schema.py` | 表结构长什么样（3 张事实表 + 6 张维度表 + 10 个索引）；表名白名单也从这里取 |
| 2 | `app/warehouse/app_schema.py` | 业务与治理表长什么样；审计表为什么"写进去就改不了" |
| 3 | `corpus/warehouse/calibration.csv` | 所有数值参数从哪来（147 条，逐条带来源类型） |
| 4 | `app/warehouse/calibration.py` | 参数怎么被校验（缺来源、权重不闭合就加载失败） |
| 5 | `app/warehouse/dimensions.py` | 渠道/品类/区域/客群/SKU 的编码与层级；大促日历 |
| 6 | `app/warehouse/generator.py` | 数据怎么造出来（向量化、分块、固定种子、真值注入） |
| 7 | `app/warehouse/groundtruth.py` | 真值怎么独立算出来（自带一份 LMDI，故意不复用被测实现） |
| 8 | `app/warehouse/verify.py` | 怎么证明这份数据可信（对账 / 指标 SQL / 恒等式 / 真值复核） |

读生成器时只要记住一句话：**所有恒等式都是"按构造成立"的**，不是巧合——
日汇总表的每个计数都由订单明细聚合而来，件单价 = GMV ÷ 销量，营收 = 销量 × 标准售价。
因此校验脚本里的"恒等式成立"检查是在验证生成逻辑，而不是在碰运气。

## 3. 指标树这条线：谁定义、谁校验、谁取数、谁算贡献

| 环节 | 归谁 | 关键约定 |
| --- | --- | --- |
| 定义 | `corpus/warehouse/metrics.yaml` | **唯一来源**：指标编码、层级、`structure`（additive/multiplicative/unresolvable）、`method`、`sql`、`sign`、口径 |
| 校验 | `packages/attribution/metrics_loader.py` | 比率型（unresolvable）禁止作为分解对象；`method` 必须与 `structure` 匹配；`sign ∈ {1,-1}`；不允许把 0 当"没有贡献" |
| 取数 | `services/attr-api/app/warehouse/verify.py` 同款写法 | `SELECT <node.sql> FROM dw.<fact_table> AS fact WHERE ...`：`fact` 是场景事实表的别名 |
| 算贡献 | `packages/attribution/tree.py` + `diff.py` / `lmdi.py` | 逐层独立守恒；默认**只拆根**（一级拆解），要下钻必须显式给 `targets` |

**最容易搞混的一点**：SQL 只负责"把两期的数取出来"，贡献额由算法算。
所以指标树节点上写的是"这个节点的值怎么查"，不是"这个节点该背多少责任"。

## 4. 三条不许越界的线（越界即缺陷，`02-流程与规范` §2.1）

1. **算法包不许 import 框架**：想在 `packages/attribution` 里连数据库、读 `.env`、调 LLM，都说明这事该放在 `services/`。
2. **`services/attr-api/scripts/` 不许被服务代码 import**：脚本是给人跑的命令行入口，服务启动路径不能依赖它们。
3. **路由层不许写算法和 SQL 文本**：路由只做参数校验与响应组装；SQL 要么来自指标字典，要么来自用例层。

## 5. 想改点东西时，从哪个入口进

| 你想做的事 | 改哪里 |
| --- | --- |
| 加一个指标（或改口径） | `corpus/warehouse/metrics.yaml`，然后跑 `verify_warehouse.py` 确认 SQL 能出数 |
| 调数仓参数（权重、增速、漏斗基准） | `corpus/warehouse/calibration.csv`（**不要**改代码里的常数——数值只允许有一个来源） |
| 加一条预埋真因 | `corpus/warehouse/truth_injections.yaml`，重新生成即自动写入真值清单与复算 SQL |
| 改表结构 | `app/warehouse/dw_schema.py` / `app_schema.py`（P3 起业务表走 Alembic，数仓表仍由生成器重建） |
| 查某个数字怎么来的 | 先在 `calibration.csv` 搜参数名，再在 `03-进度与质量` §6.3 找实测值 |
| 加业务术语 | `docs/guide/03-业务术语与口径手册.md`（T1 四条式：人话 / 怎么算 / 生活类比 / 会被追问） |

## 6. 三个常见的"这看起来不对"

1. **"订单明细和日汇总表重复了吧？"** —— 故意的。汇总表给大盘与一级拆解用（快），明细表给下钻验证用（真），
   两者由"逐日对账断言"绑死（实测 546 天全部一致）。
2. **"访客数怎么等于点击数？"** —— 定义使然：指标树要严格成立 `UV = 曝光 × CTR`，而 `CTR = 点击 / 曝光`，
   所以 `UV ≡ 点击`（D-25）。真实业务里访客会去重，这里是有意简化，已在技术规格声明。
3. **"为什么真值要另写一份 LMDI，不复用算法包？"** —— 复用就变成"用自己的答案验自己"（D-24、需求说明书 §5.12）。
   两份独立实现互为校验，测试里断言它们在 1e-9 内一致。

## 7. 分解与沙箱这条线（P3 新增）

| 步 | 文件 | 你会知道什么 |
| --- | --- | --- |
| 1 | `app/services/decomposition.py` | `MetricEngine`：按指标字典取两期数 → `decompose_tree` → 守恒断言；`Period`/`SliceFilter` 是对外口径；零值预案在 `_screen_targets` |
| 2 | `app/sandbox/policy.py` | 准入规则：SQL 走 sqlglot 的 AST（单条 SELECT + 表名白名单 + 禁函数），Python 走导入/内建/属性白名单——**父进程与子进程共用这一份** |
| 3 | `app/sandbox/child.py` | 子进程怎么执行：只读 DSN、progress handler 限扫描、`fetchmany` 限行数、受限 builtins、socket 掐死、文件写入限沙箱目录 |
| 4 | `app/sandbox/runner.py` | 父进程怎么管：策略判定 → 子进程 → 配额监控（超时/内存/CPU）→ **每次执行都写审计**（含被拦截的） |
| 5 | `app/sandbox/adversarial.py` + `corpus/eval/sandbox_adversarial.yaml` | E4 的证据：22 个用例（20 应拦截 + 2 正控）与拦截率算法 |
| 6 | `app/api/`（metrics / sandbox_api / evaluation） | 薄薄一层：参数校验 + 调用例层 + 组装响应，不写算法也不写 SQL |

**四条容易读错的地方**：

1. **沙箱不是"拦住就完事"**：`expect: allowed` 的正控用例同样重要——只拦不放的 100% 拦截率毫无意义。
2. **审计表是只写的**：`sandbox_runs` 连被拦截的记录都要写，且审计表有触发器禁止 UPDATE/DELETE。
3. **守恒判定看相对误差**（分母 `max(|Δ|, 1)`），不是绝对残差；金额上亿时绝对残差 1e-8 完全正常。
4. **遇到零值不是报个错就完了**：LMDI 要求因子严格为正，`auto_targets` 会把不满足条件的节点筛掉并写明原因
   （比如线下渠道佣金结构性为 0），既不静默替换 0，也不把整次分解拖垮。
