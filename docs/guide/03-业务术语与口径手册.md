# 业务术语与口径手册

> 版本：v1.2（P1 初版 T1 21 条 + P2 数据底座 6 条 + P3 分解与沙箱 3 条）　｜　日期：2026-09-15
> **用途**：本项目不需要你具备行业从业经验。这本手册把每个术语翻译成一句人话，并给出"在本项目里怎么算"，让你能看懂结论、也能在面试里被追问。
> **用法**：T1 每条读三遍——先读"人话"，再看"怎么算"，最后看"会被怎么追问"。T2 只需知道"我们为什么不用这个词"。

## 1. 业务总纲：整本项目就两条恒等式

```
场景 A（电商）：  GMV = 人 × 转化 × 客单        （乘法结构 → 用 LMDI 分解）
场景 B（快消）：  毛利 = 收入 − 成本            （加法结构 → 用差额分析）
```

**这两条是中学级别的直觉，其余所有术语都是这两条恒等式里零件的外号。** 行业经验只在回答"零件为什么会动"时才用得着——而那恰恰是系统要算出来的东西，不是你要背的东西。

面试时的讲述顺序固定为三段：**先讲恒等式 → 再讲口径选择（为什么用支付成功口径）→ 再讲证据（沙箱里跑了什么、结果是什么）**。

## 2. T1 术语（21 条，必懂）

### T1-01 指标异动

* **人话**：某个经营指标突然偏离了它平时的波动范围。
* **本项目怎么算**：变动幅度绝对值 > 5% **且** 相对基线的 Z 分数 > 2（阈值可配置）。
* **生活类比**：体温平时 36.5℃，今天 38.5℃——重点不是"变了"，而是"超出了正常波动"。
* **会被追问**：*你怎么知道这是异动而不是噪声？* → 答：不看单点涨跌，而是和过去 4 周同时段的基线带比较，并给出 Z 分数与正常波动区间。

### T1-02 基期

* **人话**：拿来当参照物的"过去那个时期"。（与之相对的是**现期**，即你要分析的那个时期。）
* **本项目怎么算**：现期 = 2026-06-18，基期 = 前一日（环比）或去年 06-18（同比）；基期选择必须显式记录并锁定在会话里。
* **生活类比**：称体重时先记住"上个月是 70 公斤"，这个 70 就是基期。
* **会被追问**：*为什么不用上周同期做基期？* → 答：基期一换结论就变，所以我们把它当成会话的锁定项，报告里必须写明用的是哪个基期。

### T1-03 同比 / 环比

* **人话**：同比 = 和**去年同一时期**比（用来排除季节性）；环比 = 和**紧挨着的上一个周期**比（用来看短期变化）。
* **本项目怎么算**：两者都支持，报告里必须标注用的是哪一种。
* **生活类比**：同比像"今年过年花了多少 vs 去年过年"，环比像"这个月花了多少 vs 上个月"。
* **会被追问**：*大促期间该看哪个？* → 答：两个都看。环比看当天动作（如投放调整）的效果，同比排除季节性；只给一个数是不负责任的。

### T1-04 指标树

* **人话**：把一个总指标一层层拆成更小的指标，形成一棵树。
* **本项目怎么算**：`GMV = UV × CVR × AOV`，再往下 `UV = 曝光 × CTR`、`CVR = 加购率 × 下单率 × 支付成功率`、`AOV = 件单价 × 连带率`。
* **生活类比**：家庭月支出 → 房租 + 餐饮 + 交通；餐饮再拆早/中/晚。
* **会被追问**：*指标树跟普通报表有什么区别？* → 答：报表只是把数字平铺，指标树强调父子之间必须成立（可加或可乘），否则拆出来的数字对不上总账，这正是我们强制守恒断言的原因。

### T1-05 因子拆解

* **人话**：把总变化分摊给各个组成部分，算清每部分该背多少责任。
* **本项目怎么算**：场景 A 是乘法结构用 LMDI；场景 B 外层加法用差额分析、内层乘法用 LMDI。
* **生活类比**：一家店利润少了 1 万，拆成"原材料贵了 6 千、员工加班费多了 3 千、少卖了 1 千"，三笔加起来必须正好 1 万。
* **会被追问**：*为什么非要加起来相等？* → 答：不相等就意味着漏项或重复计算，审计场景最忌讳这个；我们把它做成自动化断言 `|Σ贡献 − Δ目标| / max(|Δ目标|,1) < 1e-9`，不通过就是缺陷。

### T1-06 贡献量 / 贡献率

* **人话**：贡献量 = 某个因子导致了多少绝对变化；贡献率 = 它的变化占总变化的百分比。
* **本项目怎么算**：贡献率 = 该因子贡献 ÷ 总变动；**总变动为 0 时贡献率不定义**，只报绝对贡献并在报告里说明。
* **生活类比**：一起吃饭 AA 制，你吃了 30 元、我吃了 70 元，总账 100 元——我占 70%。
* **会被追问**：*总变动为 0 但又想比谁影响大怎么办？* → 答：这时百分比无意义（分母是 0），我们只报绝对贡献，并禁止用百分比制造误导。

### T1-07 拉动率

* **人话**：某个因子把整体"拉动/拖累"了几个百分点。
* **本项目怎么算**：以整体基期值为分母计算，各因子拉动率之和等于总变动率。
* **生活类比**：班级平均分掉了 5 分，数学一科就拖了 3 分，英语拉了 +1 分。
* **会被追问**：*它和贡献率有什么区别？* → 答：贡献率是"占总变化的份额"（加起来 100%），拉动率是"相对整体规模的百分点"（加起来等于总变动率）。两者不能混用，报告里我们会指明用的是哪个。

### T1-08 差额分析法

* **人话**：**加法结构**下最朴素的分解法：总变化 = 各加项变化之和。
* **本项目怎么算**：场景 B 中 `毛利 = 营收 − 原材料 − 物流 − 佣金 − 其他`，于是 `Δ毛利 = Δ营收 − Δ原材料 − Δ物流 − Δ佣金 − Δ其他`，直接相减。
* **生活类比**：钱包少 200 元，因为饭钱多了 150、打车多了 50，直接对账即可。
* **会被追问**：*为什么加法能直接减，乘法就不行？* → 答：乘法因子之间存在交叉项（两个因子同时变化会多出一块既不算甲也不算乙的变化），直接相减会留下说不清的残差。

### T1-09 LMDI（对数平均迪氏指数法）

* **人话**：**乘法结构**下把总变化干净地分给各因子的算法，最大特点是**残差严格为 0**。
* **本项目怎么算**：`ΔY = Σ L(Y₁,Y₀) · ln(xᵢ₁/xᵢ₀)`，其中 `L(a,b) = (a−b)/(ln a − ln b)`；要求所有因子 > 0，遇到零值走预案（替换极小值 ε 并标注，或降级分步差分）。
* **生活类比**：三个人合伙，利润从 100 涨到 130，按各自"对数平均权重"分功劳，分完不多不少正好 30，账面上没有一块钱说不清归谁。
* **会被追问**：*为什么不按比例简单分？* → 答：按比例分在三因子以上时会留下交叉残差，会出现"总变动 30，分完只有 27"的情况；LMDI 的数学性质保证残差为 0，我们可以把这一条做成自动化测试。

### T1-10 维度下钻

* **人话**：沿某个分类维度（渠道 / 品类 / 区域 / 客群）把指标拆开看，定位到底是"谁"出了问题。
* **本项目怎么算**：支持任意维度组合交叉，单次最多 3 个维度；按绝对贡献取 TOP N（默认 5）并给出覆盖率；下钻继承父层锁定切片，扩大范围必须显式操作。
* **生活类比**：全班平均分下降，先按班级看，再按科目看，最后定位到"二班的数学"。
* **会被追问**：*下钻会不会越钻越散、最后得出一个没意义的细分？* → 答：两项约束——继承锁定切片不静默扩大范围，以及报告 TOP N 的覆盖率；如果覆盖率低于阈值，我们会如实说明"原因分散，暂无单一主因"。

### T1-11 GMV

* **人话**：成交总额（商品交易总额）。
* **本项目怎么算**：取**支付成功且未取消未退款**的订单金额，按支付完成时间归集到自然日；金额以整数分存储。
* **生活类比**：一个月里真正付出去的钱之和。
* **会被追问**：*GMV 口径歧义很常见，你怎么处理？* → 答：口径写在指标字典里并版本化——"支付成功口径、按支付时间归集、退款单列"，会话与报告都记录所用版本；换口径必须生成新版本，不允许静默变更。

### T1-12 UV

* **人话**：独立访客数，去重之后的"来了多少人"。
* **本项目怎么算**：登录用户按 `user_id` 去重，游客按 `device_id` 去重；同一会话内口径不切换。
* **生活类比**：一天进店 500 人次，但其实是 300 个人（有人来了两次）。
* **会被追问**：*同一个用户换设备怎么算？* → 答：按我们声明的口径会算成两个人，这是已知偏差；所以报告中同时给出 UV 口径说明，避免把偏差当成业务变化。

### T1-13 CVR

* **人话**：转化率——一百个来访的人里，有多少完成了目标动作（下单/支付）。
* **本项目怎么算**：`CVR = 支付订单数 ÷ UV`，分子分母口径在报告中同时展示。
* **生活类比**：100 个人进店，20 个人买单，转化率 20%。
* **会被追问**：*CVR 下降一定是坏事吗？* → 答：不一定。低质量流量大量涌入（例如付费投放）会稀释 CVR，但 GMV 可能反而上升；所以我们先看结构变化（高流量低转化渠道占比是否提升），再看整体。

### T1-14 AOV

* **人话**：客单价——平均每单多少钱。
* **本项目怎么算**：`AOV = GMV ÷ 支付订单数`。
* **生活类比**：一桌菜平均花多少钱。
* **会被追问**：*AOV 下降说明什么？* → 答：可能是单价降了，也可能是买得更少（连带率降），需要再往下一层拆 `AOV = 件单价 × 连带率`，不能直接下结论。

### T1-15 客单价 / 连带率 / 加购率

* **人话**：客单价 = 每单平均金额；连带率 = 每单平均件数（一次买几件）；加购率 = 加入购物车的人数 ÷ 访客数。
* **本项目怎么算**：`客单价 = 件单价 × 连带率`；三者都在二级拆解里出现。
* **生活类比**：超市结账——你买的件数就是连带率，平均票价就是客单价。
* **会被追问**：*这三个指标怎么配合看？* → 答：客单价下降时先看是件单价降还是连带率降，二者对应完全不同的业务动作（降价促销 vs 组合推荐失效）。

### T1-16 毛利额与三类成本

* **人话**：毛利额 = 收入减去直接成本后剩下的钱；本项目把成本拆成原材料、物流履约、渠道佣金、其他四类。
* **本项目怎么算**：`毛利 = 营收 − 原材料 − 物流履约 − 渠道佣金 − 其他`，全部为不含税口径。
* **生活类比**：卖一杯奶茶 15 元，原料 4 元、外卖平台抽成 3 元、配送 2 元，剩下的 6 元就是毛利。
* **会被追问**：*为什么不直接看毛利率？* → 答：比率的分母会跟着变，无法做"份额守恒"的分解；我们用毛利额做分解，毛利率只做展示与趋势提示。

### T1-17 置信度

* **人话**：对某个结论有多相信，给它打个分。
* **本项目怎么算**：由三部分合成——显著性得分、效应量得分、数据覆盖度得分（权重固定在配置里）；低于阈值 0.6（默认）标记为"已排除"。
* **生活类比**：医生看化验单会给你一个"基本可以确定 / 还需要复查"的判断，而不是只有一个数字。
* **会被追问**：*0.6 这个阈值怎么来的？* → 答：它是可配置项，不是真理；低于阈值的假设我们**保留并标注排除理由**（而不是悄悄丢掉），报告附件里能查到每一条为什么被排除。

### T1-18 伪相关

* **人话**：两个数一起动，但并不代表一个导致了另一个——可能被第三个因素同时带动。
* **本项目怎么算**：四步检查——同切片内控制变量、时间先行性、安慰剂维度检验、样本充分性。
* **生活类比**：冰淇淋销量和溺水人数同时上升，真正原因是"天气变热"；经营里对应"大盘整体上涨，所有品类跟着涨"。
* **会被追问**：*你怎么排除？* → 答：如果某个假设在某维度切片内部不再成立，或在一个"理论上不该成立"的安慰剂维度上同样显著，就判定为共同驱动趋势并排除。

### T1-19 业务大事件日历

* **人话**：把大促、政策变化、系统故障、竞品动作等外部事件记在时间表上，用来解释指标波动。
* **本项目怎么算**：异动窗口**前后各 3 日**内匹配，且事件影响维度与异动维度有交集才入链。
* **生活类比**：店里生意突然变差，先看看门口是不是在修路。
* **会被追问**：*会不会所有问题都甩锅给外部事件？* → 答：两个约束——时间窗口与维度交集都必须满足，不满足的只列为"待观察"；命中时也只在因果链里标为**外生变量**，不会覆盖内部因子的贡献。

### T1-20 What-If / 弹性系数

* **人话**：What-If = "如果调整某个参数，指标会变成什么样"；弹性系数 = 参数变化 1%，指标大约变化百分之几。
* **本项目怎么算**：只对**可干预因子**（预算、价格、佣金率）推演，取值范围限制在历史区间（默认 ±30%），输出**区间**与前提条件。
* **生活类比**：把空调从 26℃调到 24℃，预计电费会增加多少——只能给区间，不能给精确值。
* **会被追问**：*这个推演能信吗？* → 答：它是基于历史弹性的**区间推演**，附带前提条件和把握度，用途是给策略排序，不是承诺结果；同一输入必须输出完全一致的结果（可复现）。

### T1-21 守恒

* **人话**：各因子的贡献加起来，必须严格等于总变动。
* **本项目怎么算**：每层强制 `|Σ贡献 − Δ目标| / max(|Δ目标|, 1) < 1e-9`，并在报告与接口里输出实际残差（LMDI 应输出残差为 0）。
* **生活类比**：AA 制分账，每个人分到的加起来必须等于账单总额，差一分钱也要查出来。
* **会被追问**：*为什么要求这么严？* → 答：如果允许"差不多对得上"，结论就无法审计；我们把守恒做成自动化断言并用上百万组随机数据验证，失败即视为实现缺陷。

## 3. T2 术语：我们保留能力，但不用这些黑话

| 黑话 | 我们说成什么 | 说明 |
| --- | --- | --- |
| Shapley 价值分解 | "按占比分摊" | 对外用占比贡献法表述；实现上按维度占比分摊差值，**明确说明它是启发式、非唯一解** |
| 敏感性分析 | "调参看曲线" | 只做单点弹性 + 参数曲线，不做完整敏感度矩阵 |
| 反事实仿真 | "如果…会怎样" | 已并入 What-If 情景对比 |
| 交叉残差 | "为什么必须用 LMDI 才对得平" | 只在解释 LMDI 必要性时提一次 |
| p 值 / 显著性水平 | "这个差异有多大概率是巧合" | 保留计算，表述白话化；统计上使用置换检验 + 固定种子 |
| 变异贡献率 | "某因子拖累了几个百分点" | 与拉动率统一表述，避免同义词混用 |
| 杜邦分析法 | 不使用 | 本质就是指标树，重复包装 |
| 桑基图 | 不使用 | 瀑布图 + 透视表已覆盖 |

## 4. 数据底座术语（P2 补充，同样是"能脱口复述 + 举一个类比"）

### T1-22 事实表 / 维度表

* **人话**：事实表记"发生了什么、发生了多少"（一天卖了多少钱）；维度表记"这是谁、在哪、什么时候"（哪个渠道、哪个品类、哪个区域）。
* **本项目怎么算**：事实表 3 张（电商日汇总、订单明细、快消日汇总）；维度表 6 张（日期、渠道、品类、区域、客群、SKU）。
* **生活类比**：超市小票是事实表（一笔一笔），货架标签和门店名册是维度表（查一下就知道"这笔是谁卖的"）。
* **会被追问**：*为什么订单明细和日汇总都留着，不是重复吗？* → 是刻意冗余：日汇总给大盘和一级拆解用（快），明细给下钻核对用（真）。
  两者靠"逐日对账断言"绑定——明细加起来必须精确等于汇总，实测 546 天全部一致。

### T1-23 星型模型

* **人话**：一张事实表放中间，几张某维度表围着它，像星星。
* **本项目怎么算**：`fact_ecom_daily` 连到 渠道 / 品类 / 区域 / 客群 四张维度表；`fact_fmcg_daily` 连到 渠道 / SKU / 区域。
* **生活类比**：体检报告（事实）围着"谁、什么时间、查了哪几项、在哪家医院"（维度）转，换任一维度都能切一遍。
* **会被追问**：*为什么不直接做成一张大宽表？* → 宽表会随维度膨胀、口径变更时到处改；星型让"加一个维度"只加一张表和一个外键。

### T1-24 口径（caliber）

* **人话**：同一句话"成交额"，算法不同结果就不同，所以必须把算法写死并起个名字。
* **本项目怎么算**：`gmv_paid_success` = 支付成功且观察期内未退款的订单金额（按支付时间归集，退款单列）；口径变更必须升版本，历史会话与报告绑定当时版本。
* **生活类比**："体重"是早上空腹称还是饭后称？两个数字都对，但混着比就没意义。
* **会被追问**：*为什么不用下单口径？* → 下单口径会把未支付、已取消、已退款都算进来，GMV 立刻变成"意愿"而不是"成交"。

### T1-25 真值预埋（ground truth）

* **人话**：造数据的时候故意埋下"已知原因"，并提前算好它应该占多少责任，作为事后判卷的标准答案。
* **本项目怎么算**：`corpus/warehouse/truth_injections.yaml` 声明 4 条注入（如"付费投放渠道支付成功率下滑 22%"），生成器写入 `app.ground_truth`，并附一条独立 SQL 供任何人复算。
* **生活类比**：老师出题时就把答案封存好；不能等学生交卷后，拿学生的答案当标准答案。
* **会被追问**：*真值会不会就是系统自己算的？* → 不会。真值由生成器的解析式独立算出（自带一份 LMDI 实现，不调用被测算法包），并用独立 SQL 复算（实测 4/4 通过）。

### T1-26 对账断言

* **人话**：两个本该相等的东西，程序每次都替你比一遍，不等就报错。
* **本项目怎么算**：订单明细按天聚合后，支付单数 / 销量 / GMV / 退款额必须等于日汇总表，逐日比对（546 天）。
* **生活类比**：收银台的日结：抽屉现金必须等于流水，差一分也要查。
* **会被追问**：*断言失败时怎么办？* → 校验脚本非 0 退出，数仓不允许进入下游阶段；这不是"警告"，是"不许交付"。

### T1-27 只读打开（immutable）

* **人话**：不是"用权限拦住你写"，而是**打开方式就是只读**，数据库自己拒绝任何写操作。
* **本项目怎么算**：沙箱连接串固定 `file:dw.db?mode=ro&immutable=1`，再叠一层 `PRAGMA query_only=ON`；业务表根本不在这个文件里。
* **生活类比**：不是打字员被禁止改写档案，而是他拿到的是复印件的塑封本——物理上写不进去。
* **会被追问**：*那和数据库只读角色比，谁更强？* → 就"这一条连接能不能写"而言，文件级只读更硬也更好验证（5/5 写操作被拒）；
  但 SQLite 没有角色层，所以"同机同用户直接读 `app.db` 文件"这一层必须靠 OS 权限兜底，我们在技术规格里如实写清。

### T1-28 数据沙箱

* **人话**：给"跑数"这件事圈一块地——只能看数仓、只能读、只能跑一条查询，跑歪了当场掐掉并记一笔。
* **本项目怎么算**：独立子进程 + 只读打开（`mode=ro&immutable=1`）+ AST 白名单（只允许单条 SELECT、表名必须在数仓白名单内）+
  配额（20 秒硬超时、行数上限、扫描步数上限、内存上限）+ 全量审计。
* **生活类比**：银行柜台的防弹玻璃 + 单一窗口 + 全程录像：能办正事，办不了别的事，而且每一笔都有记录。
* **会被追问**：*隔离到什么级别？* → 如实说 **进程级**，不是容器级；能防住写库、越权读表、外网访问、资源耗尽；
  防不住同机同用户直接读文件、内核漏洞逃逸、极慢查询侧信道——这三条写在技术规格 §6.3，不夸大。

### T1-29 对抗测试与拦截率

* **人话**：不光说"我这儿安全"，而是自己先当一次坏人，把能想到的坏招挨个试一遍，再报告拦下了几成。
* **本项目怎么算**：22 个用例（越权读表、多语句、注释绕过、挂外部库、读文件、加载扩展、`import os/socket`、
  借 pandas 联网、越界写文件、死循环、内存炸弹、超大结果集、交叉连接扫描炸弹…），拦截率必须 100%，
  每条都要有审计记录；**同时必须有正控**（正常查数与正常计算要能跑通）。
* **生活类比**：消防演练：不是贴一张"已配备灭火器"的告示，而是真的点一把火看看能不能灭掉。
* **会被追问**：*只拦不放也能 100%，怎么证明不是一刀切？* → 正控用例就是为这个问题准备的：
  正常 SQL 与 numpy 计算必须在同一套配置下跑通，误拦同样算缺陷（我们把它单列为 `false_blocks`）。

### T1-30 零值预案

* **人话**：乘法拆解要求每个因子都严格大于 0，现实里总有几个因子是 0（比如线下渠道不计佣），得先想好怎么办。
* **本项目怎么算**：默认**不拆并写明原因**（`auto_targets` 会把该节点筛掉，报告里列出"子因子非正"）；
  只有在明确选择替换策略时才把 0 换成 ε，并打上 `zero_substituted` 标记——绝不让 0 悄悄变成一个小数。
* **生活类比**：分账时有人没点菜，你不能给他随便编一个金额；正确做法是说清"这一项为 0，不参与分摊"。
* **会被追问**：*那结果不就少了这块吗？* → 少的是"无法定义"的那部分，报告里明写原因；
  强行算出来的数字比缺失更危险，因为它看起来像结论。

## 6. 面试口径（把术语讲成业务，而不是背词典）

**三段式标准答法**：

1. **恒等式**："GMV = 人 × 转化 × 客单，所以我把 GMV 的变化拆成这三块的责任。"
2. **口径选择**："GMV 我用支付成功口径、按支付时间归集，退款单列——因为用下单口径会把未支付和退款混进来。"
3. **证据**："假设是系统生成的，但验证在沙箱里跑，产出的是数值、样本量和显著性；贡献之和必须严格等于总变动，容差 1e-9，不通过就是缺陷。"

**高频追问与答法**（详见 `docs/submission/面试问答册.md`，P7 完成）：

| 追问 | 答法要点 |
| --- | --- |
| 数据是真实的吗？ | 明确说：数据是合成的，但**带预埋真值**；准确率类指标基于合成数据集，守恒、性能、并发、越权拦截这些硬指标与数据真假无关 |
| LLM 会不会算错数？ | 数值全部由确定性算法计算，LLM 只出假设草案与报告文字，每条结论都能落到可复现的查询 |
| 你的沙箱真的安全吗？ | 讲隔离等级（受限子进程、无网络、只读角色、配额）与**残余风险**，并给出对抗测试拦截率，不说"绝对安全" |
| 为什么只做两个场景？ | 因为方法论只有两套（加法/乘法），两个场景正好把它们都验证到；再多的场景是重复劳动 |
