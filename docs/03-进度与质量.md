| 2026-09-15 | `other_cost` 节点引用不存在的列 `fact.other_cents` | 指标 SQL 一跑就报 no such column | 事实表列为 `other_cost_cents`，已修正；这类错误只能靠"真跑一遍 SQL"暴露 |
| 2026-09-15 | 快消真值漏减了未被注入的成本项 | 校验报 2 条真值与 SQL 复算不一致（差 7387 万 / 45182 万分） | 真值核算改为"毛利 = 其它项 − 被注入项"，并对每条真值做独立 SQL 复算，4/4 通过 |
| 2026-09-15 | 沙箱连接查不到 `dw.` 前缀 | 只读连接直接打开 `dw.db`，`dw.fact_ecom_daily` 报 no such table | 抽出 `open_readonly_connection()`：服务与沙箱子进程共用同一处只读实现（`app/db.py`） |
| 2026-09-15 | FastAPI `TestClient` 触发 `StarletteDeprecationWarning`（建议改 `httpx2`） | 测试仍通过，仅提示 | 记在此处备查；等 P3 引入依赖时再决定是否跟随，不为一条 warning 换依赖 |
| 2026-09-15 | 子进程"沙箱"最初没装受限 builtins | `exec` 默认注入真实 builtins，等于没有沙箱 | 改为显式 `__builtins__ = _safe_builtins(...)`，并加 socket 掐死与文件守卫；对抗用例 15/16/20 覆盖 |

| 2026-09-15 | 快消经销商渠道下钻报 `LMDI 因子非正` | 线下渠道佣金结构性为 0，LMDI 要求因子严格为正 | 按 §5.2 零值预案：`auto_targets` 先筛节点，非正就"不拆并写明原因"，不静默替换 0 |
| 2026-09-15 | 内存炸弹用例在 Windows 上没被拦截 | `bytes(8MB)` 走按需分页，RSS 不增长，父进程轮询看不到 | 用例改用真实驻留的列表分配，并在 YAML 注明原因（选例不能骗自己） |
| 2026-09-15 | `git push` 报连不上 github.com | git 里配的 `https.proxy=127.0.0.1:11678` 已无进程监听；后来连 `127.0.0.1:12000` 也失效（代理客户端换了配置，Windows 系统代理开关还是关的） | 把全局 `http(s).proxy` 指到**当前在监听**的端口（先是 12000，随后 12001），每次都用 `git ls-remote` 当场验证再推。**教训：代理端口是会变的，别把端口当成固定配置**——连不上时先 `Test-NetConnection 127.0.0.1 -Port <端口>` 探一遍（远程地址见 §11） |

### 6.5 业务讲解卡（P2 必交，讲不出不进 P3）

**这一段在业务上干什么。** 真实企业几乎不会把经营明细给外部项目用，就算给了也没有"标准答案"。所以本阶段做了两件事：
第一，把公司 18 个月的经营数据按"天 × 渠道 × 品类 × 区域 × 客群"摆成能对上账的表（订单明细加起来必须等于日汇总，一分钱都不能差）；
第二，在造数据的同时**故意埋下已知原因**——比如"6 月 5—11 日，付费投放渠道的支付成功率掉了 22%"——并把这条真因的应得贡献额事先算好存进真值清单。
后面 P3 起的归因算法算出来的结论，就要跟这份事先封存的答案对账。

**生活类比。** 像给运动员做体测：先记录他平时的各项指标（基线），再明确告诉他"这周左脚踝缠了绷带"（已知伤病），
然后才检验队医的诊断准不准。如果等诊断完再回头编一个"伤病原因"，那份诊断就没有任何说服力——这正是我们禁止用系统自己的分解结果去回填真值的原因。

**被追问时怎么答（三段）**

1. *为什么必须用合成数据？* → 真实数据拿不到，且真实数据没有标准答案；合成数据的价值在于**同时给出数据和真因**，
   这样"归因准不准"才能量化（Top-1 命中率、贡献额相对误差），而不是只靠演示看起来像。
2. *真值会不会是系统自己算出来的？* → 不会。真值由生成器的解析式独立算出（`groundtruth.py` 自带一份 LMDI 实现，
   不调用被测算法包），并且每条真值都附一条独立 SQL，可以直接从数仓复算：实测 4/4 通过。
   另外还有"聚合表 = 明细表"的逐日对账（546 天全部一致），保证底盘数据本身没被动过手脚。
3. *这份数据像真实企业数据吗？* → 像到"能用来考核"的程度，但不是真实数据。品类年增速、线上渗透率（25.66%）、
   餐饮占比（11.41%）、PPI 成本漂移（+2.0%）都取自国家统计局 2026-08 / 1—8 月公开数据；平台转化率、佣金率、
   大促倍率这类没有权威公开口径的，全部标为"自定参数"（共 147 行参数，逐条可查）。我们从不声称它是真实企业数据。

### 7.5 业务讲解卡（P3 必交，讲不出不进 P4）

**这一段在业务上干什么。** 干两件事。第一件是**分账**：总指标变了，要拆成"谁的责任、各占多少"，
乘法恒等式（GMV = 人 × 转化 × 客单）用 LMDI，加法恒等式（毛利 = 收入 − 成本）用差额分析，
而且规定**每一层的贡献加起来必须严丝合缝等于总变化**，不通过就报错，不允许"差不多对得上"。
第二件是**给"跑数"上牢笼**：模型或人写出来的查询只能看数仓、只能读、只能跑一条 SELECT，
超时就掐、越权就拦，而且每一次执行都留痕（连被拦下的也要留）。

**生活类比。** 分账像 AA 制：一桌人吃完饭，每个人该出多少必须能加回账单总额，差一分钱都要查出来——
这就是"守恒"。沙箱像银行柜台的防弹玻璃 + 单一窗口 + 全程录像：能办正事，但办不了别的事，
而且办过的每一笔都有记录；窗户纸捅不破这件事，我们不用嘴说，用 20 个"坏人用例"当场测给你看。

**被追问时怎么答（三段）**

1. *怎么证明沙箱不是摆设？* → 20 个对抗用例：越权读业务表、多语句拼接、注释绕过、挂外部数据库、
   `readfile`/`load_extension`、`import os`/`socket`、借 pandas 绕路联网、越界写文件、死循环、
   内存炸弹、超大结果集、交叉连接扫描炸弹——实测 100% 拦截且 22/22 都有审计记录。
   同时有 2 个**正控**（正常查数、正常计算必须能跑通）：只拦不放的 100% 拦截率是没有意义的。
2. *隔离到什么级别？* → **进程级**，不是容器级、更不是虚拟机级。能防住写入、越权读表、外网访问、
   无限资源占用与危险模块导入；防不住同机同用户直接读文件（Windows 上没有 rlimit 精确计量 CPU）、
   内核漏洞逃逸、以及借极慢查询做侧信道——这三条写在 `01-技术规格` §6.3，我们不夸大。
3. *为什么不干脆用容器？* → 本机 Docker 守护进程常不启动（已实测），项目硬约束就是"不依赖 Docker"（D-06）；
   所以用受限子进程 + 只读打开 + 配额 + 全量审计，并把残余风险写清楚——这是一次有意识的取舍，不是没想过。

### 7.6 本阶段的取舍与已知偏差（如实声明）

| 项 | 事实 | 为什么这样处理 |
| --- | --- | --- |
| 经销商渠道的佣金结构性为 0 | 线下渠道不计佣，`commission_rate = 0`，LMDI 要求因子严格为正 | 按 `01-技术规格` §5.2 的**零值预案**：不下钻、在报告里写明原因，绝不把 0 悄悄替换成 ε |

### 8.5 本阶段的取舍与已知偏差（如实声明）

| 项 | 事实 | 为什么这样处理 |
| --- | --- | --- |
| E1 贡献额中位误差 6.8% 高于参考目标 5% | 真值记录的是"纯注入贡献"，分解看到的是"两期全部变化"（含季节性、大促与自然波动） | 不调窗口凑数；P6 用配套对照窗口（同星期对齐、剔除大促日）收紧，口径差异写进术语手册 |
| 模型通道未经真机验证 | 本机 `LLM_API_KEY` 为空 | 通道实现完整（请求体、JSON 解析、失败降级），但只有"无密钥→模板"路径在本机实测；文档与记录一律标注 `source=template`，把"未验证"写在明处 |
| 假因在合成数据里较好识别 | 数据由固定参数与注入生成，共同驱动只有季节性与大促 | 因此 E3 的 0% 误纳率**不能**外推到真实业务数据；这条会进问答册与报告口径 |
| 安慰剂判据含工程折中 | "同样显著"实现为"显著且强度 ≥ 假设切片的 80%" | 只看显著性时，本数据的季节性是共同趋势，会把所有假设判成伪相关（首轮实测 5/5 全排除）；阈值写成代码常量并可复算 |
| 单条链路 36~38 s | 每条假设取证 10~12 次沙箱调用（含四步检查） | 先保"证据链可复现"；进程池与并行留给 P6 的并发章节 |
| 首轮误纳 20% → 0% 的迭代 | 第一轮 1/5 误纳：一条陷阱的命题其实为真（餐饮渠道营收确实贡献 13%），另一条暴露"缺少贡献占比门禁" | 两处真实修正：① 补"贡献占比 <5% 不能称为主因"（依据 §5.11）；② 把那条伪陷阱换成真正非因果的用例（单一 SKU 被当公司级主因）。不是调参凑数，改动与证据都留在这里 |

### 8.6 业务讲解卡（P4 必交，讲不出不进 P5）

**这一段在业务上干什么。** 前三阶段解决"数算得对不对"，这一段解决"结论靠不靠得住"。系统会像分析师一样先提出几条候选解释
（例如"是付费渠道的转化率拖的"），然后**逐条拿去数仓里查证**：切片内与其他渠道比是不是真的差、差异有多大概率是巧合
（置换检验 1 万次）、原因是否早于结果、换个本不该成立的维度是否也"显著"、样本够不够。最后只留站得住的，
把站不住的连同**排除理由**一起摆出来。

**生活类比。** 像侦探破案：不能因为"两人同时出现在现场"就定案。要看动机（共同原因）、看时间线（谁先谁后），
再做对照（换个无关现场做同样的测试，如果到处都"成立"，那多半是巧合而不是线索的功劳）。

**被追问时怎么答（三段）**

1. *假设是模型提的吗？* → 通道支持模型（DeepSeek），但**数值一律不经过模型**：模型只出假设文本与取数草案，
   草案还必须过沙箱才能执行；本机没有密钥，所以这次跑的是确定性模板，记录里逐条标着 `source=template`。
2. *怎么证明不是"看着像就下结论"？* → 每条假设都有证据链：沙箱 SQL 摘要、样本量、p 值、效应量、覆盖天数，
   全部落库（`hypotheses` + `evidence`）；另有四步伪相关检查，以及"贡献占比 <5% 不能叫主因"的门禁。
3. *真实数据上也灵吗？* → 诚实说：**样本小、数据是合成的**。E1 只有 4 条真因、E3 只有 5 条陷阱，
   0% 误纳率来自"合成数据的共同驱动只有季节性/大促"这个前提；真实数据更脏更复杂，这部分材料里不吹。
