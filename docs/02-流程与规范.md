# 流程与规范

> 版本：v1.0（P1）　｜　日期：2026-09-15
> 本文件的权威范围：**怎么做**——阶段流程、工程规范、验证档位、质量门禁、范围裁剪台账、文档维护规则。范围与验收标准见 `00-需求说明书.md`。

## 1. 阶段流程（每个阶段都走这七步）

| 步 | 动作 | 产物 |
| --- | --- | --- |
| 1 | 读文档：确认本阶段范围与出口条件（`00-需求说明书` 第 14 节） | — |
| 2 | 写范围与出口条件：把本阶段要做/不做写清楚，避免边做边扩 | 阶段开篇写进 `03-进度与质量.md` |
| 3 | 实现：先写算法与断言，再写接口，最后写前端 | 代码 + 单测 |
| 4 | 自检：按第 3 节的验证档位跑，不留"回头再跑" | 命令与实测输出 |
| 5 | **业务讲解卡**（不可跳过）：用大白话讲清"这一段在业务上干什么"，并给出生活类比；**讲不出来不进入下一阶段** | 一段文字 + 类比 + 被追问时的答法 |
| 6 | 更新文档：`03-进度与质量` 记实测数据；有新决策写 `04-决策记录`；术语补充进 `guide/03-业务术语与口径手册` | 三处更新 |
| 7 | 里程碑提交：一次提交对应一个阶段 | Conventional Commits |

**阶段与出口条件**（与 `00-需求说明书` 第 14 节一致）：P1 文档定稿 → P2 数仓与指标树引擎 → P3 分解算法与沙箱 → P4 假设生成与事件关联 → P5 会话与前端 → P6 评测与扩写 → P7 材料与部署。

## 2. 工程规范

### 2.1 目录职责（越界即缺陷）

| 目录 | 职责 | 禁止 |
| --- | --- | --- |
| `packages/attribution/` | **纯算法**：指标树解析、差额分析、LMDI、守恒断言、弹性估计 | 禁止 import FastAPI / SQLAlchemy / 任何 IO；必须可用纯函数单测 |
| `services/attr-api/` | FastAPI 服务：路由、依赖注入、会话、权限、审计、沙箱调度、报告组装 | 禁止把算法逻辑写在路由里 |
| `services/attr-api/scripts/` | 运维与演示脚本（生成数据、跑评测、演示链路） | 禁止被服务代码 import |
| `apps/attr-web/` | Vue 3 控制台（五页面） | 禁止绕过 API 直连数据库 |
| `corpus/` | 合成数仓的参数与事件定义、评测集用例 | 不放生成后的大文件（落 `.data/`，已 gitignore） |
| `infra/` | 部署与数据库初始化脚本 | 不依赖 Docker（本项目约定） |

**依赖方向单向**：`apps → services → packages`，禁止反向依赖。

### 2.2 数值与统计规范（本项目最容易被追问的部分）

* 金额在事实表中以**整数分**存储；展示与报告按元保留 2 位小数。
* 分解计算用 `float64`；**浮点比较一律用相对误差**，禁止 `==` 比较浮点数。
* 守恒断言统一走一个函数：`assert_conservation(contributions, delta, tol)`，不允许各处自己写比较。
* 任何统计检验必须固定随机种子，保证同一输入可复现。
* **禁止**把大模型输出当作数值来源：数值只能来自确定性计算；大模型只产出假设文本、SQL 草案、报告文字。
* 除法必须显式处理分母为零：能定义才输出百分比，不能定义就只输出绝对值并说明。

### 2.3 代码与提交规范

* 提交信息遵循 Conventional Commits：`feat: / fix: / docs: / refactor: / test: / chore: / perf:`；一个阶段一个里程碑提交。
* 每个模块的公开函数必须有 docstring，说明**业务含义**（而不只是参数类型）。
* 错误处理：禁止裸 `except`；沙箱拦截与业务校验必须区分（前者是安全事件，要审计；后者是用户错误，要提示）。
* 日志结构化，字段固定包含 `session_id` / `step_id` / `actor` / `duration_ms`。
* 不提交 `.env`、密钥、依赖目录、生成后的大数据集与导出文件。

## 3. 验证档位（改完代码按档跑，别每次都跑全量）

| 档位 | 内容 | 预计耗时 | 什么时候用 |
| --- | --- | --- | --- |
| 快速档 | `ruff check .` + `pytest`（含守恒单测） | ≈1 分钟 | 每次改完代码 |
| 定点档 | `pytest -k <用例>` 或评测 `--only <题号>` | ≈0.5 分钟 | 只改了某类判定/某个指标 |
| 标准档 | 快速档 + 小样本生成（10 万行）+ 一条端到端演示脚本 | ≈3 分钟 | 一片功能做完 |
| 完整档 | 标准档 + 500 万行生成 + 归因评测集全跑 + 沙箱对抗 + 并发 | ≈15–25 分钟 | 阶段收尾 / 出对外数字前 |

**规矩**：对外宣称的任何数字，都必须能在完整档下重跑一次；跑不出同样量级的数字，就不许写进 README 与材料。

## 4. 质量门禁（不达标不算完成）

| 门禁 | 标准 |
| --- | --- |
| 守恒 | 加法 / 乘法 / 混合树三种结构各 ≥100 组随机数据，相对误差 < 1e-9，通过率 100% |
| 沙箱 | 对抗用例拦截率 100%（逃逸、越权读表、超配额、网络访问、写业务表） |
| 评测 | 归因评测集出数并留档（Top-1 / Top-3 / 贡献额相对误差）；伪相关陷阱误纳率 ≤10% |
| 一致性 | 报告三格式导出与页面内容字段级一致 |
| 可复现 | 固定种子重跑，指标波动 ≤ ±1pp |

**明令禁止**：硬编码结论数字；跳过守恒断言"先跑通再说"；把模型输出当数值；用预录输出伪造演示；未实测就写指标。

## 5. 范围裁剪台账与变更流程

* 被砍与降级的功能、能力、术语，逐条记录在 [`00-项目共识确认书.md`](00-项目共识确认书.md) 第 7.2 节（源头）与 `00-需求说明书.md` 第 2.2 节（需求侧）。
* **变更流程**：任何人（包括我）要改范围，必须先回写确认书台账——写明"改什么、为什么改、代价是什么"——再由你确认。**不允许静默扩大或缩小范围。**
* 新增能力只要不违反第 4 节门禁、不引入新的外部依赖，可以边做边补进 `00-需求说明书` 的能力表。
* **已执行过的变更（作为流程样例）**：P2 把数据库从 PostgreSQL 改为 SQLite。回写位置：
  `04-决策记录` D-22（决策 + 理由 + 两条代价）、`01-技术规格` §1/§3/§6/§7（实现口径改写）、
  `00-项目共识确认书` §4.1 与 §9（形态与风险登记）、本文件 §7（阻塞处理记录）。没有一处是"顺手改掉不提"。

## 6. 文档维护规则

* 归位规则见 [`README.md`](README.md)；**不新建第 5 份顶层文档**。
* 业务术语与代码同步：每完成一个模块，先把该模块用到的业务名词补进 `guide/03-业务术语与口径手册.md`，再写代码注释。
* 实测数字只写在 `03-进度与质量.md` 与 README 的指标表，且在 `03` 里必须附上"命令 + 日期 + 环境"三要素。

## 7. 阻塞处理

遇到阻塞（环境不可用、依赖装不上、外部接口不通）时：

1. 先记进 `03-进度与质量.md` 的"环境问题"一节，写清现象、诊断证据、已尝试的处置、建议路径；
2. 能绕过就绕过，并在文档里注明绕过的代价；
3. 绕不过就停下来说明阻塞点，不硬撑、不假装跑通。

## 8. 提交包规范（课程提交兼容）

* 目录命名：`组名_姓名_项目_行业`（例如 `X组_张三_经营归因_电商零售`）。
* 提交内容：代码文件（**不含依赖**）+ 测试截图；`README.md` 写明一键演示命令与实测指标。
* 本项目额外材料（术语手册、面试问答册、威胁模型、安全审查、评测报告）一并放入提交包，它们属于加分项而不是负担。
